# Assinaturas no WhatsApp — contrato interno das Fases 2 e 3

Leia `docs/plano-assinaturas-whatsapp.md` (decisões D1–D11, 14 cuidados, Fases 2 e 3) antes.
Este arquivo fixa as **assinaturas e formatos** que as peças das duas fases compartilham. Quem implementa
uma peça segue o contrato; quem consome também. Mudança de contrato = atualizar este arquivo.

Peças e donos (Fase 2 ‖ Fase 3, em duas ondas):
- **Onda 1 · S3B** — Fase 3 back: migration + `whatsapp-subscriptions.service.ts` + cupons + eventos + `whatsapp-outbox.service.ts` + mudanças em `whatsapp-charges.service.ts`/`whatsapp-crm.service.ts`/DTOs/admin/module.

- **Onda 2 · B2R** — Fase 2 runtime (`whatsapp-bot.service.ts`, simulador com fixture, ponte `charge_paid`) + E2E `wa_bot_crm_e2e.mjs`.
- **Onda 2 · S3F** — Fase 3 front (Produtos, aba Assinaturas do cliente, Cupons, juros/multa em Cobranças).

## 1. Motor do bot (`back/src/whatsapp/bot/wa-bot.engine.ts`) — puro, sem banco

### 1.1 Tipos novos de bloco (`TYPES` + `walk` + `handleInput` + `handleEvent` + `validateDefinition`)
`crm_identify · crm_register · crm_subscribe · crm_info · crm_invoice · crm_cancel · crm_pause · crm_change_plan · crm_update`.
Portas (sourceHandle) por bloco — **nomes fixos**:

| bloco | portas | observações |
|---|---|---|
| `crm_identify` | `found`, `not_found`, `invalid` | `invalid` = documento/código com formato inválido após `retries`; se `invalid` não estiver ligada, cai em `not_found`. Mais de um cliente no número → o motor manda a lista numerada (`choose_text`) e espera `waiting_for:'crm_choose'`; a escolha vai por `found`. (A porta `choose` do plano foi absorvida pelo motor.) |
| `crm_register` | `done`, `cancel`, `failed` | `cancel` = cliente respondeu "cancelar"/"2" na confirmação. |
| `crm_subscribe` | `paid`, `subscribed`, `expired`, `declined`, `no_customer`, `failed` | `subscribed` só quando `charge_now:false` ou a 1ª cobrança não existe (trial / valor 0). `declined` = disse não na confirmação. |
| `crm_info` | `out`, `no_customer` | |
| `crm_invoice` | `sent`, `nothing_open`, `no_customer`, `failed` | |
| `crm_cancel` | `canceled`, `kept`, `no_subscription`, `no_customer`, `failed` | |
| `crm_pause` | `paused`, `no_subscription`, `no_customer`, `failed` | |
| `crm_change_plan` | `changed`, `kept`, `no_subscription`, `no_customer`, `failed` | |
| `crm_update` | `out`, `cancel`, `no_customer`, `failed` | |

Regra geral: porta `no_customer` / `no_subscription` / `failed` **não ligada** → o motor envia o texto correspondente (`no_customer_text`, `no_subscription_text`, `failed_text`, com defaults em português) e termina o fluxo (`finish`), como um bloco sem continuação.

### 1.2 `data` de cada bloco (defaults entre parênteses; o front cria com `createNodeData`, o motor tolera ausência)
- `crm_identify`: `title`, `mode` (`'org'`) ∈ `org|phone|ask_doc|ask_code`, `ask_text` (vazio = `ctx.identity.ask_doc_text` / `"Qual é o seu <code_label>?"`), `not_found_text` (vazio = `ctx.identity.doc_not_found_text`), `invalid_text` (vazio = `ctx.identity.doc_invalid_text`), `retries` (3), `choose_text` ("Encontrei mais de um cadastro neste número. Qual deles?"), `found_text` (opcional, enviado ao achar). `mode:'org'` ⇒ `ctx.identity.require_doc ? 'ask_doc' : 'phone'`. `phone` ⇒ usa `ctx.customers` (sem pedir nada). Ao achar: `state.customer_id`, `ctx.customer` = o achado (o motor pode mutar `ctx.customer` como já faz com `ctx.chatTagIds`).
- `crm_register`: `title`, `intro_text` (opcional), `fields: [{key, label, question, required (true), validate}]`, `confirm` (true) + `confirm_text` ("Confira seus dados:\n{{resumo}}\n\n1️⃣ Confirmar\n2️⃣ Corrigir / cancelar"), `done_text` ("Cadastro concluído ✅"), `link_role` (`'owner'`), `failed_text`. `key` ∈ `name | doc | email | code | address.zip | address.street | address.number | address.district | address.city | address.state | notes | custom.<key>`. `validate` default por key: name→`name`, doc→`doc`, email→`email`, address.zip→`cep`, address.state→`uf`, resto→`any`. Campo opcional: cliente responde `pular`/`-`/`não` → fica vazio. Em qualquer pergunta, `cancelar` → porta `cancel`. Mecânica: `state.crm = { step, fields: {} }`, `waiting_for:'crm_register'`; na confirmação `waiting_for:'crm_confirm'`. Resumo `{{resumo}}` = "Nome: X\nCPF: …" (doc mascarado). Ao confirmar → ação `crm_create_customer` + `waiting_for:'crm_wait'`.
- `crm_subscribe`: `title`, `product_id` (`'choose'`) ∈ `'choose' | 'from_var' | <uuid>`, `product_ids: []` (subconjunto quando `choose`; vazio = todos os ativos), `choose_text` ("Qual plano você quer?"), `method` (`'pix'`) ∈ `pix|boleto|ask`, `ask_method_text` ("Como prefere pagar?\n1️⃣ PIX\n2️⃣ Boleto"), `charge_now` (true), `confirm` (true) + `confirm_text` ("Você escolheu *{{produto.nome}}* por *{{produto.valor}}*{{produto.periodo}}.\n\n1️⃣ Confirmar\n2️⃣ Agora não"), `declined_text`, `subscribed_text` ("Assinatura ativada ✅ …"), `paid_text` ("Pagamento confirmado ✅ …"), `expired_text`, `no_customer_text`, `failed_text`. `from_var` lê `state.vars.produto_id` (preenchido pelo menu `source:'products'`). Produto `once` (avulso) também passa por aqui (vira assinatura avulsa + cobrança única). Ao confirmar → ação `crm_subscribe` + `waiting_for:'crm_wait'`; resultado com cobrança → `state.charge` + `waiting_for:'charge'`; eventos `charge_paid` → `paid_text` → porta `paid`; `charge_expired` → `expired_text` → `expired`. Enquanto espera `charge`: entrada com `paguei|pago|comprovante|transferi|feito` → ação `charge_check {charge_id}`; outra entrada → `info`.
- `crm_info`: `title`, `what` (`'status'`) ∈ `status|next_charge|subscriptions|data|custom`, `template` (vazio = template padrão por `what`), `no_customer_text`. Só monta texto (sem ação de runtime) com as variáveis da §1.5.
- `crm_invoice`: `title`, `which` (`'open'`) ∈ `open|last|choose`, `method` (`'same'`) ∈ `same|pix|boleto|both`, `choose_text`, `sent_text` ("Enviei a 2ª via acima 👆"), `nothing_open_text` ("Você não tem cobrança em aberto 🙂"), `no_customer_text`, `failed_text`. `open` = pendente mais antiga; `last` = pendente mais recente; `choose` = lista numerada (`waiting_for:'crm_choose'`). Escolhida → ação `crm_send_charge {charge_id, method}` + `waiting_for:'crm_wait'`.
- `crm_cancel`: `title`, `subscription` (`'single'`) ∈ `single|choose`, `choose_text`, `ask_reason` (true), `reason_text` ("Pode me dizer o motivo?"), `reasons: []` (vazio = `ctx.cancel_reasons`; lista numerada; qualquer outro texto = motivo livre), `retention_text` (opcional, enviado antes da confirmação), `confirm_text` ("Confirma o cancelamento de *{{assinatura.produto}}*?\n\n1️⃣ Sim, cancelar\n2️⃣ Não, manter"), `policy` (`'product'`) ∈ `product|immediate|end_of_cycle`, `canceled_text` ("Cancelado. {{assinatura.fim_texto}}"), `kept_text`, `no_subscription_text`, `no_customer_text`, `failed_text`. `single` com mais de uma assinatura viva = pergunta qual (vira `choose`). Fluxo: escolher → motivo → retenção+confirmação → ação `crm_cancel_subscription {subscription_id, reason, policy}` + `waiting_for:'crm_wait'`.
- `crm_pause`: `title`, `max_days` (30), `ask_until` (true), `ask_text` ("Por quantos dias quer pausar? (até {{max_dias}})"), `days` (usado quando `ask_until:false`), `paused_text` ("Pausado até {{assinatura.pausa_ate}} ⏸️"), `no_subscription_text`, `no_customer_text`, `failed_text`. Resposta = número de dias (1..max_days) → ação `crm_pause_subscription {subscription_id, days}`.
- `crm_change_plan`: `title`, `product_ids: []` (vazio = todos os ativos, menos o atual), `choose_text`, `confirm` (true) + `confirm_text`, `changed_text` ("Plano trocado para *{{produto.nome}}* ✅"), `kept_text`, `no_subscription_text`, `no_customer_text`, `failed_text`. → ação `crm_change_plan {subscription_id, product_id}`.
- `crm_update`: igual ao `crm_register` (`fields`, `confirm`, `confirm_text`, `done_text`) mas exige cliente e gera ação `crm_update_customer {fields}`.
- `condition`: regra nova `source:'customer'` com `key` ∈ `status | product | days_overdue | verified | has_open_charge | has_subscription | custom.<key>`; ops: status→`is|is_not` (valor `ok|overdue|none|inactive|paused`), product→`is|is_not` (uuid), days_overdue→`gt|lt`, verified/has_open_charge/has_subscription→`is` (valor `true|false`), custom.<key>→`eq|neq|contains|not_contains|empty|not_empty`. Sem cliente: status=`none`, verified=false, demais vazios.
- `menu`: `source` (`'options'`) ∈ `options|products`; com `products`: opções = `ctx.products` ativos (filtrados por `data.product_ids` quando não vazio), rótulo "Nome · R$ X/mês"; portas dinâmicas `opt-<product_id>` + `invalid` (igual ao menu normal). Escolha grava `state.vars.produto_id`, `state.vars.produto` (nome) e `state.vars.opcao`.

### 1.3 Estado e contexto
```ts
type BotState = {
  node_id; status; retries; wait_until; last_input; vars; pix;
  waiting_for: 'menu'|'question'|'pix'|'wait'
    |'crm_identify'|'crm_choose'|'crm_register'|'crm_confirm'|'crm_subscribe'|'crm_cancel'|'crm_pause'|'crm_change_plan'|'crm_update'
    |'crm_wait'   // ação de CRM enviada ao runtime; espera `crm_result`
    |'charge'     // cobrança criada; espera `charge_paid|charge_expired`
    | null;
  customer_id: string | null;
  crm: { step?: number|string; fields?: Record<string,string>; options?: {id:string; label:string}[]; purpose?: string;
         subscription_id?: string|null; product_id?: string|null; method?: string|null; reason?: string|null } | null;
  charge: { id: string; amount_cents: number; description: string; due_at: string|null; pix_code?: string|null; boleto_url?: string|null } | null;
};
type BotCustomer = {
  id: string; name: string; first_name: string; doc_masked: string; code: string; email: string;
  status: 'ok'|'overdue'|'none'|'inactive'|'paused'; verified: boolean; custom: Record<string,string>;
  subscriptions: { id; product_id: string|null; product_name; price_cents; price_label; billing; status; next_due_at: string|null /*YYYY-MM-DD*/; next_due_label; days_overdue: number; due_day: number|null; cancel_at: string|null; paused_until: string|null }[];
  open_charges: { id; amount_cents; amount_label; description; due_at: string /*YYYY-MM-DD*/; due_label; days_overdue: number; kind; pix_code: string|null; boleto_url: string|null; status }[];
};
type BotProduct = { id; name; description: string|null; price_cents; price_label; billing; billing_label; trial_days: number; cancel_policy: 'end_of_cycle'|'immediate'; active: boolean };
type BotContext = {
  contact; vars?; chatTagIds; now; settings;
  customer: BotCustomer | null;        // cliente do número (1º) — o motor pode trocar ao identificar
  customers: BotCustomer[];            // todos os clientes vinculados ao número
  products: BotProduct[];              // produtos ATIVOS da org
  identity: { require_doc: boolean; use_code: boolean; code_label: string; ask_doc_text: string; doc_not_found_text: string; doc_invalid_text: string };
  cancel_reasons: string[];
};
```
`emptyState()` devolve `customer_id:null, crm:null, charge:null`. `handleInput`/`handleEvent` copiam `crm`/`charge` como copiam `vars`.
Persistência (runtime): `vars.__crm`, `vars.__customer_id`, `vars.__charge` — o motor não sabe disso.

### 1.4 Ações novas (`BotAction`) e eventos
```ts
| { type: 'crm_lookup'; by: 'doc'|'code'; value: string }
| { type: 'crm_create_customer'; fields: Record<string,string>; link_role: string }   // atualiza se já há cliente no número
| { type: 'crm_subscribe'; product_id: string; method: 'pix'|'boleto'; charge_now: boolean; node_id: string }
| { type: 'crm_send_charge'; charge_id: string; method: 'same'|'pix'|'boleto'|'both' }
| { type: 'charge_check'; charge_id: string }
| { type: 'crm_cancel_subscription'; subscription_id: string; reason: string|null; policy: 'product'|'immediate'|'end_of_cycle' }
| { type: 'crm_pause_subscription'; subscription_id: string; days: number }
| { type: 'crm_change_plan'; subscription_id: string; product_id: string }
| { type: 'crm_update_customer'; fields: Record<string,string> }
```
Todas as ações `crm_*` deixam `state.status='waiting'` + `waiting_for:'crm_wait'` (exceto `charge_check`, que não muda o estado). O runtime executa e devolve:
```ts
handleEvent(def, prev, event, ctx, payload?)
event: 'wait_done'|'pix_paid'|'pix_expired'|'crm_result'|'charge_paid'|'charge_expired'
payload (crm_result): { ok: boolean; error?: string;
  customer?: BotCustomer|null; customers?: BotCustomer[];      // identify / register / update
  subscription?: BotCustomer['subscriptions'][number];          // subscribe / cancel / pause / change_plan
  charge?: BotState['charge'] | null;                           // subscribe (1ª cobrança) / invoice
  product?: BotProduct }
payload (charge_paid|charge_expired): { charge_id: string }
```
`crm_result` só é aceito com `waiting_for:'crm_wait'` (senão `info` e nada muda). Ao receber, o motor atualiza `ctx.customer`/`state.customer_id` quando vier `customer`, e segue pela porta conforme §1.1/§1.2. `charge_paid` só é aceito com `waiting_for:'charge'` e `charge_id === state.charge.id` (entrega tardia é tratada pelo runtime, que reconstrói o estado, como no PIX).

`cliente.nome · cliente.primeiro_nome · cliente.documento (mascarado) · cliente.codigo · cliente.email · cliente.status (em dia|em atraso|sem assinatura|inativo|pausada) · cliente.produto · cliente.produtos · cliente.valor · cliente.vencimento · cliente.dia_vencimento · cliente.<custom>`;

Fonte: `ctx.customer` (assinatura = a escolhida em `state.crm.subscription_id`, senão a 1ª viva; cobrança = a de `state.charge`, senão a aberta mais antiga; produto = `state.crm.product_id` em `ctx.products`). Variável desconhecida continua virando vazio.

### 1.6 `validateAnswer` ganha `doc` (CPF **ou** CNPJ válidos), `cnpj`, `cep` (8 dígitos), `uf` (2 letras), `code` (1..32 chars). `validateDefinition` cobre os blocos novos (produto fixo precisa de uuid; `crm_register`/`crm_update` precisam de ≥ 1 campo com `key`).

### 1.7 Simulador (`POST /whatsapp/bot/simulate`, B2R)
Corpo: `{flow_id|definition, settings, state?, input?|event?, event_payload?, crm_fixture?}`.
`crm_fixture: { customer: BotCustomer|null, customers?: BotCustomer[], products?: BotProduct[], identity?: Partial<identity>, lookup?: Record<string, BotCustomer> /* doc|code → cliente */, cancel_reasons?: string[] }`.
Com fixture o serviço resolve as ações `crm_*` **em memória** e já devolve o fluxo continuado (chama `handleEvent('crm_result')` sozinho), acrescentando à lista de ações uma pseudo-ação `{ type:'charge', charge: BotState['charge'] }` quando uma cobrança "foi criada" (código `PIX-SIMULADO-…`) para o front mostrar o cartão e os botões "Pagou"/"Expirou" (eventos `charge_paid`/`charge_expired` com `event_payload:{charge_id}`). Sem fixture: as ações `crm_*` viram `{type:'info', text:'Procuraria o cliente pelo CPF …'}` e o estado fica em `crm_wait` (o chamador pode mandar `event:'crm_result'` + `event_payload`). Resposta: `{state, actions, ended, customer}`.

### 1.8 Decisões do motor/front (B2E, 12/10/2026) — o que ficou diferente ou além do texto acima
Implementado em `wa-bot.engine.ts` (teste `docs/tools/wa_bot_engine_test.mjs`, 165/165) e em `front/.../whatsapp/bot/*`. O runtime (B2R) deve seguir isto:
- **Tipos:** os campos novos de `BotContext` (`customer/customers/products/identity/cancel_reasons`) são **opcionais no TS** (`?`) para o `whatsapp-bot.service.ts` atual continuar compilando; o motor trata ausência como "sem cliente / sem produto / org sem exigir documento". `handleEvent(def, prev, event, ctx, payload?)` — o 5º argumento é opcional; eventos antigos funcionam com 4. Tipos exportados: `BotEvent`, `BotEventPayload`, `BotCustomer`, `BotSubscription`, `BotOpenCharge`, `BotProduct`, `BotIdentity`, `BotCharge`, `BotCrmStep`, `BotWaitingFor`; helpers exportados: `customerVars(state, ctx, extra?)`, `currentCustomer(state, ctx)`, `fillVars(text, state, ctx, extra?)` (4º arg = `{resumo, max_dias}`), `productLabel(p)` ("Nome · R$ X/mês"), `fmtDateBR`, `periodOf`, `CRM_TEXTS` (textos padrão), `REGISTER_FIELD_DEFAULTS`, `CRM_TYPES`. `formatBRL` usa `Intl` (o espaço entre "R$" e o número é U+00A0).
- **Cliente "atual"** = `currentCustomer`: `state.customer_id` procurado em `ctx.customers`/`ctx.customer`, senão `ctx.customer`. Ao identificar (phone, choose ou `crm_result`), o motor faz `state.customer_id = c.id`, `ctx.customer = c` e acrescenta em `ctx.customers`. Todo bloco que exige cliente também grava `state.customer_id` quando usa o cliente do número.
- **Portas de erro × textos:** `no_customer/no_subscription/nothing_open/failed` seguem a regra do §1.1 (texto só quando a porta NÃO está ligada; ligada = sem texto). **`declined_text` e `kept_text` são SEMPRE enviados** (o cliente respondeu "não" e precisa ouvir algo) e depois o motor segue pela porta. `cancel` do register/update: sem texto quando ligada; não ligada manda um texto padrão de "cadastro cancelado".
- **`crm_identify`:** no modo `phone` o `not_found_text` só é enviado se o dono escreveu um (padrão = silêncio; a porta `not_found` costuma levar ao cadastro); nos modos com pergunta (`ask_doc/ask_code`, ou `org` com `require_doc`) vazio = `ctx.identity.doc_not_found_text`. `invalid_text` vazio = `ctx.identity.doc_invalid_text` (código: texto fixo). Após `retries` inválidos o motor vai por `invalid` (ou `not_found` se `invalid` não estiver ligada) **sem** mandar `not_found_text`. `crm_result` com `customers.length > 1` → lista numerada (`crm_choose`); `ok:true` sem `customer` = não encontrado. `found_text` (opcional) é enviado ao achar, com `{{cliente.*}}` já preenchidas.
- **Escolhas numeradas:** `state.crm.options = [{id,label}]`; aceitam número, keycap, "opção N", texto exato do rótulo. Inválida → `invalid_option_text` das Configurações (ou `data.invalid_text`) e, após `max_retries`, a lista é reenviada (sem porta). `waiting_for` da escolha: `crm_choose` para cliente/cobrança, e o do bloco (`crm_subscribe/crm_cancel/crm_pause/crm_change_plan`) para plano/assinatura. A sub-etapa fica em `state.crm.step` (`'product'|'method'|'confirm'|'sub'|'reason'|'days'|'action'|'lookup'|'ask_doc'|'ask_code'|<índice do campo>`).
- **Confirmações (sim/não):** "1"/sim/confirmar/ok/pode/quero… = sim; "2"/não/n/cancelar/manter/corrigir… = não; outra resposta = repete o texto de confirmação (após `max_retries` continua repetindo; não há porta).
- **`crm_register`/`crm_update`:** `fields[]` pode trazer `id` (só para a UI). `validate` default por key: name→name, doc→doc, email→email, **code→code (1..32 chars)**, address.zip→cep, address.state→uf, demais→any; `question` vazia = pergunta padrão (`REGISTER_FIELD_DEFAULTS`; `code` usa `ctx.identity.code_label`; custom usa o rótulo). Campo opcional: pergunta ganha " _(ou responda *pular*)_" e aceita `pular/-/não/nenhum/skip/próximo`. `cancelar/desistir/sair/parar` em qualquer pergunta → `cancel`. Resposta inválida repete a dica do tipo (sem limite). `{{resumo}}` = "Rótulo: valor" só dos preenchidos, `doc` mascarado. `crm_update` com 0 campos válidos ou `crm_register` sem campo → `failed`.
- **`crm_subscribe`:** `choose` com **exatamente 1 produto** elegível não pergunta (escolhe direto); 0 produtos → `failed` (texto "não há planos disponíveis"). `from_var` lê `state.vars.produto_id` (gravado pelo menu de produtos, que também emite `set_var produto_id`); produto inexistente/inativo → `failed`. Ao escolher, o motor grava `vars.produto_id`/`vars.produto`. Enquanto `waiting_for:'charge'`, o motor NÃO envia texto (quem envia a cobrança é o runtime via `charges.create(send:true)`); o simulador mostra o cartão pela pseudo-ação `charge`. `charge_paid`/`charge_expired` aceitam `payload.customer`/`payload.subscription` para atualizar o cliente antes de montar `paid_text`.
- **`crm_invoice`:** `open` = menor `due_at`; `last` = maior; `choose` com 1 cobrança não pergunta. `state.charge` recebe a cobrança escolhida antes da ação (vale para `{{cobranca.*}}` no `sent_text`); `crm_result.charge` (2ª via recalculada) sobrescreve.
- **`crm_cancel`:** assinaturas elegíveis = `active|overdue|paused` **sem `cancel_at`**; `reasons` vazio = `ctx.cancel_reasons`; sem nenhum motivo cadastrado a pergunta vai sem lista (texto livre). `state.crm.reason` = rótulo escolhido ou texto livre (≤ 255). `crm_result.subscription` é aplicado no cliente antes de `canceled_text` (é de onde sai `{{assinatura.fim_texto}}`).
- **`crm_pause`:** elegíveis = `active|overdue` (já pausada → `no_subscription`); `data.choose_text` (extra, não estava no contrato) e `data.invalid_text` (extra) para a pergunta da assinatura e para dias inválidos ("Responda só com o número de dias, de 1 a {{max_dias}}"); `max_days` limitado a 1..365; `ask_until:false` usa `days` (limitado a `max_days`). A resposta aceita "7 dias" (só os dígitos).
- **`crm_change_plan`:** elegíveis = `active|overdue|paused`; `data.choose_sub_text` (extra) para escolher a assinatura quando há mais de uma; lista exclui o produto atual; nenhum outro produto → `failed`.
- **`crm_info`:** `template` vazio usa o modelo de `CRM_TEXTS.info[what]`; `custom` sem template cai no de `status`.
- **`condition` `source:'customer'`:** `days_overdue` = máximo entre as assinaturas vivas e as cobranças abertas; `custom.<key>` é comparado normalizado (sem acento/caixa) e a chave é lida em minúsculas.
- **`menu` `source:'products'`:** com 0 produtos ativos o motor nem envia o menu — vai direto pela porta `invalid` (ou termina). Palavras-chave da opção = nome do produto.
- **Variáveis extras:** `produto.descricao`; `cliente.<custom>` com a chave em minúsculas; `assinaturas.lista` vazia = "Você ainda não tem assinatura."; `cobrancas.lista` vazia = "Nenhuma cobrança em aberto 🙂"; `cobranca.dias_atraso` = da cobrança em `state.charge` (procurada em `open_charges`) ou da mais antiga aberta; `assinatura.fim_texto` usa DD/MM.
- **Front:** `createNodeData` grava os textos padrão nos blocos (editáveis); textos vazios = padrão do motor (placeholder mostra qual). `useBot()` ganhou `products` (`GET /whatsapp/products`, `null` = carregando) e `crmSettings` (`GET /whatsapp/crm-settings` → `{custom_fields, identity}`); `outputsOf(type, data, settings, products)` (4º arg novo, usado pelo menu de produtos); `validateFlow(nodes, edges, {…, products, crmSettings})` com nível **`info`** novo (badge/lista em azul). Simulador: painel "Cliente fictício" (Não é cliente / Em dia / Em atraso / 2 no número + "Org exige CPF") monta `crm_fixture` com `products` reais (ou 2 de exemplo), `lookup` = `{ '52998224725': cliente, 'CLI-001': cliente }`, `identity`, `cancel_reasons`; manda em todo POST; pseudo-ação `{type:'charge', charge}` vira cartão + botões Pagou/Expirou (`event_payload:{charge_id}`); e o painel também lê `state.waiting_for==='charge'` + `state.charge.id` da resposta para mostrar os botões.

### 2.3 Decisões da implementação (S3B, 12/10/2026) — o que ficou além/diferente do texto acima
- **`meta.auto_charge`** (novo, opcional): quem cria a 1ª cobrança. Padrão `true` para `panel|import|api|system` e **`false` para `source:'bot'`**. Com `true`, `createSubscription` guarda `custom.first_charge = {amount_cents, due_at, description, auto:true}` e emite `hooks.emit('subscription_first_charge', {orgId, subscription, customer, first_charge, meta})` → `WhatsAppChargesService` cria e envia na hora (best-effort; sem gateway fica a marca) e o runner diário (`firstChargeFor`, 1b) é a rede de segurança. **O bot cria a cobrança ele mesmo** com `charges.create({ customer_id, subscription_id, amount_cents: first_charge.amount_cents, due_at: first_charge.due_at, description: first_charge.description, chat_id: <jid>, session_id, bot:{flow_id,node_id} }, 'bot')`; `charges.create` com `subscription_id` limpa `custom.first_charge` (`subscriptions.clearFirstCharge`).
- **Regras da 1ª cobrança** (`createSubscription`): `once` → preço cheio (com cupom), `next_due_at` null. Trial → `trial_ends_at = início + dias`, `next_due_at` = fim do trial (ou o 1º `due_day` depois dele, se `due_day` veio no DTO), sem cobrança. Entrada **no dia do vencimento** → preço cheio hoje, `next_due_at` = +1 ciclo. `prorate` (padrão) → `prorateCents` hoje, `next_due_at` = 1º vencimento. `prorate:false` → preço cheio hoje, `next_due_at` = 1º `due_day` após 1 ciclo. `due_day` ausente = dia do início (máx. 28). `first_charge.due_at` = hoje (ou `start_date` se futura). Valor < R$ 1,00 → `first_charge` null.
- **Pagamento da 1ª cobrança não avança `next_due_at`** (ela paga o período até lá); as demais avançam `addMonths(due, ciclo, due_day)` quando `due ≥ next_due_at`. `charges.settle` chama `subscriptions.markPaid(orgId, subId, {id, amount_cents, due_at, paid_via}, meta)` (evento `paid`; `activated` no 1º pagamento; `overdue → active`).
- **Desconto**: `discount_cents` sobre `price_cents` enquanto `discount_until` (null = sempre) ≥ vencimento da cobrança (`discountActive`). Cupom `once` → `discount_until` = data da 1ª cobrança (hoje se há cobrança imediata, senão `next_due_at`); `months` → início + N meses; `forever` → null. `amountFor(sub, product?, forDate?)` usa `forDate ?? sub.next_due_at`. Cobrança recorrente com valor < R$ 1,00 (crédito cobre) → `markPaid` com `paid_via:'credit'` e avança sem cobrar.
- **Troca de plano**: só entre recorrentes, assinatura `active|overdue` (pausada/cancelada → 400). Crédito = `creditCents(amountFor atual, max(next_due − ciclo, started_at), next_due, hoje)` **só se `last_paid_at` existe**; vira `discount_cents` com `discount_until = next_due_at`, `coupon_id` = null, `billing` acompanha o produto novo, cobranças PENDING da assinatura são canceladas (regeradas pelo runner com o valor novo). Sem cobrança da diferença (upgrade) — por desenho.
- **Cancelamento**: `policy:'product'` lê `cancel_policy` do produto (sem produto = `end_of_cycle`). `immediate` (ou sem `next_due_at`, ou vencimento já passou, ou pausada) → `canceled` + `cancel_at = hoje` + cancela PENDING (gateway + `charge_canceled`) + texto `canceled`. `end_of_cycle` → `cancel_at = next_due_at`, cancela só as PENDING com `due_at ≥ cancel_at`, texto `cancel_scheduled`; o runner (`dailyMaintenance`) fecha no dia (evento `canceled` com `data.effective:true`, texto `canceled`). Evento `canceled` é gravado **duas vezes** no fim de ciclo (`scheduled:true` ao agendar, `effective:true` ao fechar). `reactivate` desfaz um agendamento (`cancel_at` null) ou reativa uma cancelada (`next_due_at` = 1º `due_day` a partir de hoje).
- **Pausa**: `until` (YYYY-MM-DD) ou `days` (padrão 30, máx. 365); guarda `custom.paused_from` e `custom.status_before_pause`. `resume` empurra `next_due_at` pelos dias **efetivamente** pausados (`min(paused_until, hoje) − paused_from`); o runner retoma quando `paused_until ≤ hoje` (`source:'system'`).
- **Reajuste** (`readjust`): no mês configurado, 1× por ano por assinatura (`custom.readjusted = 'YYYY'`), só recorrentes `active|overdue|paused`; quem entrou há menos de 60 dias no ano pula aquele ano. Só o percentual da org (não há percentual por produto).
- **Aviso de trial**: D-3 (`trial_ends_at = hoje + 3`), 1 vez (`custom.notified.trial_ending = 'YYYY-MM-DD'`).
- **Carência**: `overdue` só com `dias de atraso ≥ 1 + grace` (`grace` = `product.grace_days`, senão `grace_days_default`); grava evento `overdue` 1× (o `updateMany` só muda `active → overdue`). A etiqueta "Inadimplente" e o hook `charge_overdue` continuam no D+1 (são da cobrança, não da assinatura).
- **Juros/multa**: `charges.amountWithPenalty(charge, today?, cfg?)` é **async** (lê as configurações) e devolve `{ amount_cents, base_cents, fee_cents, interest_cents, days_late }`. O shape da cobrança ganhou `penalty` (mesmo objeto, só em PENDING), `base_amount_cents`, `bot_flow_id`, `bot_node_id`. `resend` recria PIX/boleto só quando o valor (ou o `kind` pedido) mudou — idempotency `wacharge-<id>-pix-r<valor>-<hoje>` — e usa o texto `second_copy` quando há atraso (variáveis novas `cobranca.valor_original|multa|juros|dias_atraso`); sem gateway → 400 "Configure o gateway…". `POST /whatsapp/charges/:id/resend` aceita corpo `{ kind? }`.
- **`charges.create`**: `chat_id` aceita uuid da conversa **ou jid** (`<n>@c.us`, exige `session_id`); com `customer_id` + `chat_id`, o cliente é o informado e o número é o da conversa. `dto.bot` grava `bot_flow_id/bot_node_id`; `base_amount_cents` = valor na criação.
- **Hooks novos**: `subscription_created`, `subscription_first_charge`, `subscription_changed`, `subscription_canceled` (`policy`, `scheduled?`), `subscription_paused`, `subscription_resumed`, `subscription_reactivated`, `charge_canceled` (`reason: 'manual'|'subscription'`), `charge_expired`, `outbox_sent`. Payload de cobrança (`charge`) = linha inteira do Prisma (com `bot_flow_id/bot_node_id/base_amount_cents`).
- **Fila (`WhatsAppOutboxService`)**: `enqueue(orgId, { session_id, chat_id, kind, payload: { messages:[{kind?,text?,media_id?}] | text/media_id, mark?, charge?:{id,which} }, run_at?, dedupe_key? })` (dedupe = `uk_waoutbox_dedupe`, colisão devolve null), `enqueueForCustomer(orgId, {id, contact_id}, kind, payload, {run_at?, dedupe_key?})` (resolve o número: conversa mais recente num número conectado → qualquer conversa → número conectado + telefone; null = sem como), `cancelPending(orgId, {kind?, chat_id?, dedupe_prefix?})`, `sendNow(orgId, sessionRow, jid, {kind,text?,mediaId?}, extra)` = helper ÚNICO de "enviar + gravar OUT" (as cobranças usam), `summary(orgId)`. Worker: tick 5 s, lote 60, claim `pending→sending`, `outbox_per_minute` por número (memória), org sem acesso → +1 h, número desconectado → +5 min, `PacingService.canSend` falhou → amanhã 09:00 BRT, erro → 30 s / 2 min / `failed` na 3ª; `payload.charge` → grava `sent_at`/`reminders` na cobrança ao sair. Dedupes usados: `charge:<id>:<which>:<dia>`, `sub:<id>:<texto>:<dia>`.
- **`runDailyFor`** devolve `{ generated, first_charges, reminders, overdue, queued, closed, resumed, trial_notices, readjusted, errors }`; recorrentes só com `gateway_ready`; `charge_days_before` do produto sobrescreve `days_before_due`; `cancel_at ≤ next_due_at` pula a geração.
- **Settings**: `ChargeSettings`/`DEFAULT_CHARGE_SETTINGS` e a normalização moraram para `wa-charge-settings.util.ts` (puro); `whatsapp-charges.service.ts` reexporta. `fillCrmVars`/`formatBRL` moraram para `wa-crm-vars.util.ts` (o CRM reexporta). `billing` ganhou **`semiannual`** (6 meses; `billing_interval_months` de 1/3/6/12 ajusta o enum do produto).
- **Produtos**: `shapeProduct` devolve `trial_days, grace_days, prorate, cancel_policy, billing_interval_months, cycle_months, charge_days_before, reminder_rules, entitlement, custom, category`; `PUT /whatsapp/products/:id` é parcial (chaves `undefined` ignoradas).
- **`POST /whatsapp/customers/:id/subscriptions`** devolve o **cliente** (compat) + `subscription` (shaped, com `first_charge`); `coupon_code` vem via `shapeMany`. `updateSubscription`/`removeSubscription` do CRM continuam (edição manual sem evento).
- Testes: `docs/tools/wa_subscription_math_test.mjs` (40 casos fixos sobre o `dist`) e `docs/tools/wa_subscription_engine_e2e.mjs` (servidor; cabeçalho explica os limites sem gateway/número real).

- **Trial sem dia escolhido:** `due_day` passa a ser o dia em que o teste acaba (máx. 28) e `next_due_at = nextDueFromDate(trial_ends_at, due_day)` — os ciclos seguintes ficam alinhados.
- **Pausa:** cancela no gateway as cobranças PENDING da assinatura com vencimento a partir de hoje (as vencidas continuam em aberto); a retomada volta a gerar pelo runner.
- **Cupom:** o uso é reservado de forma atômica antes de gravar a assinatura (`updateMany … used < max_uses`); se a gravação falhar, o uso é devolvido.
- **Fila:** 1 envio por número por rodada (rodada a cada 2 s), espaçados por `60 s ÷ outbox_per_minute`; linha presa em `sending` (back reiniciou no meio) volta para `pending` em 10 min (e todas no boot); `sent_at` da cobrança = 1º envio (lembrete não sobrescreve).

## 7. Revisão de qualidade das Fases 1–4 (13/10/2026) — o que mudou nos contratos acima

Varredura com 4 revisores (assinaturas/identidade, bot, pagamentos, front) → ~100 achados corrigidos no mesmo dia. O que altera o comportamento descrito nas seções anteriores:

### 7.1 Bot (§1, §6)
- **Dois níveis de verificação no estado:** `vars.__verified` = clientes conferidos pelo **documento** (ou já vinculados ao número) e `vars.__seen` = clientes achados por **código/matrícula** (só leitura nesta conversa, nunca vincula). `ctxFor` só chama `ensureLinked` para ids de `__verified`; os dois entram em `ctx.customers` (até 5), o que corrige a escolha entre vários clientes do mesmo CPF (`crm_choose`) em produção.
- **Escrita exige documento ou vínculo** (`ownCustomerId(state, ctx, {write:true})`): cancelar, pausar, trocar plano, atualizar dados, assinar e **2ª via** (`crm_send_charge`) recusam o cliente só visto por código com `user_text` "Para alterar a assinatura ou os dados, confirme o seu CPF/CNPJ (o código sozinho só permite consultar)." → porta `failed`. A cobrança só muda de conversa (session/chat) para vinculado/doc-verificado. A condição "documento verificado" = doc-verificado-ou-vinculado.
- **`BotEventPayload.user_text`** (novo): recusa amigável enviada SEMPRE antes de seguir por `failed` (substitui `failed_text`). No back, `BotUserError extends BadRequestException` é a única exceção cuja mensagem vira `user_text`.
- **`crm_identify` com `crm_result {ok:false}`** = FALHA (freio, erro) → `user_text` + porta `invalid` (ou `not_found` se `invalid` não estiver ligada), sem `not_found_text`. "Não achei" continua sendo `{ok:true, customers:[]}`.
- **Freio:** 6 `crm_lookup` por conversa por hora (memória); a 7ª → "Muitas tentativas de identificação por aqui 🙏 …".
- **Cadastro pelo bot:** `notes` é **acrescentada** (`[bot DD/MM/AAAA HH:MM] texto`, teto 20 000), nunca substitui; `crm_update` não altera `doc`/`code` já preenchidos (recusa amigável); `crm_create_customer` num número que já tem cliente: cliente **sem** documento → completa o cadastro; cliente **com** documento e o digitado é outro → cliente NOVO (`another:true`), o antigo fica intocado.
- **Confirmações:** `yesNo(input, context)` ignora pontuação e testa a 1ª palavra; na confirmação do `crm_cancel` "cancelar"/"sim, cancelar" = sim e "manter" = não. `{{assinatura.fim_texto}}` após cancelamento imediato = "O cancelamento vale a partir de agora."
- **`currentCustomer`:** `state.customer_id` que não está no contexto → `null` (`no_customer`), nunca cai no `ctx.customer`.
- **`crm_change_plan`:** só `active|overdue` sem `cancel_at` e não-`once`; destinos sem `once`. **`crm_cancel`** com `subscription:'choose'` pergunta mesmo com 1 assinatura. **`crm_subscribe`** exclui planos com assinatura viva (active/overdue/paused); fixo/`from_var` já assinado → `already_text` + `failed`; o runtime trava também no banco.
- **Menu de produtos** sem aresta para o produto escolhido → porta `invalid`, senão `out`, senão `unavailable_text` ("Essa opção não está disponível no momento 😕 Escolha outra:") e repete o menu; `validateFlow` avisa por produto não ligado.
- **Retentativas:** dias da pausa e perguntas de cadastro/atualização respeitam `max_retries` (3ª inválida → `failed`); `CANCEL_WORDS` na pausa → `canceled_text` + `failed`; só número no começo ("7", "7 dias").
- **Esperando a cobrança:** qualquer mensagem (≠ "paguei…") recebe `waiting_text` ("Ainda estou aguardando o pagamento ⏳ … digite *{{comando_reiniciar}}*"); variável nova `comando_reiniciar` (1ª `restart_keywords`, default "menu"); palavra de reinício sai de qualquer espera.
- **Textos novos (editáveis no inspetor):** `crm_subscribe.waiting_text`, `crm_subscribe.already_text`, `crm_pause.canceled_text`, `menu.unavailable_text` (só produtos). Períodos: `semiannual` ("por semestre"/"/semestre"); `once` = `''`.
- **`customerVars`:** campos personalizados são escritos ANTES dos fixos (um campo "nome" não sobrescreve `cliente.nome`). `MAX_CRM_DEPTH` atingido → `crm_result {ok:false}` (segue por `failed`). `deliverLateCharge` semeia `crm.subscription_id/product_id` (texto de pago com o produto certo).
- **`PUT /whatsapp/bot/flows/:id`** → 403 para MEMBER quando o fluxo está **ativo** (membros editam fluxos desligados). Simulador: lookup por código não marca `verified`; `next_due_at` simulado segue o período do plano; `crm_mode:'org'` separa doc/código.
- **`botModel.js`:** nomes reservados `produto_id, produto, opcao, cliente`; `isKnownCrmVar(k, customFields)` devolve `true|false|'custom-missing'` e `validateFlow` avisa `{{cliente.x}}` desconhecido.

### 7.2 Assinaturas / CRM / fila (§2, §3, §5)
- **Início no passado** (`plan()`): `rollForward` leva o 1º vencimento ciclo a ciclo até ≥ hoje (nunca cobra meses para trás); pró-rata conta de hoje. Trial com início no passado termina hoje. Importação (`source:'import'`) nunca inicia trial.
- **PUT legado da assinatura** (`subData`): `status` diferente → 400 "Use as ações cancelar/pausar/retomar/reativar."; `product_id` diferente → 400 "Use trocar plano."; mudar `due_day` sem `next_due_at` explícito → 1ª data com o novo dia ≥ vencimento atual (nunca re-cobra período pago); eventos `manual_edit {fields, from, to}` e `price_changed {reason:'manual'}`.
- **Apagar cliente/assinatura** cancela cobranças em aberto no gateway e na fila (`cancelOpenCharges`), devolve o uso do cupom. `WhatsAppCrmService` injeta `WhatsAppOutboxService`.
- **Crédito na troca de plano:** denominador = ciclo inteiro; crédito limitado ao que foi PAGO no período (sem pagamento ou pago com crédito → 0); só cobranças com `due_at >= hoje` são canceladas (dívida antiga fica); crédito maior que o novo preço fica guardado (`custom.plan_credit`) e é consumido ciclo a ciclo.
- **Cupom `once`** sem cobrança imediata → desconto vale para a cobrança do `next_due_at` (não "hoje"). Cupom com `product_ids` em assinatura sem produto → "Cupom válido só para produtos específicos."
- **Status ao vivo respeita a carência** (`liveStatus(sub, today, graceDays)`; `shapeMany` carrega `grace_days` do produto / `grace_days_default`).
- **Pausa/retomada:** re-snap ao `due_day`, `trial_ends_at` deslocado, `overdue` volta como `overdue` com o `next_due_at` antigo. `custom` sempre via `patchCustom` (relê antes de gravar; só a própria chave). `cancel`/`reactivate` limpam `custom.first_charge` (e `trial_charge` no imediato). Fechamento diário com `updateMany` guardado. Aviso de trial: `cancel_at: null` e janela de 3 dias (1×).
- **`custom` do cliente:** `sanitizeCustom` (40 chaves, 500 chars) e chaves reservadas (`first_charge, trial_charge, paused_from, status_before_pause, readjusted, notified, plan_credit`) nunca vêm do cliente. DTOs de update via `PartialType` (`UpdateProductDto`, `UpdateCustomerDto`, `UpdateCouponDto`) — ValidationPipe volta a valer; `payment_method_id` validado (`resolvePaymentMethod`: do cliente, ativo, só com `payment_method:'card'`).
- **Escala:** manutenção diária e reajuste por cursor (lotes de 500, filtro em SQL), clientes carregados em lote; `listCustomers` com `groupBy`; datas de negócio do CRM em BRT (`todayUTC` removido); `isDateStr` rejeita datas impossíveis; só um titular por cliente (`setRole('owner')` rebaixa o anterior; re-vincular com papel padrão não rebaixa o titular); limite de 50 assinaturas conta só não-canceladas; `markPaid` em assinatura cancelada → evento `paid_after_cancel` + warn.
- **Fila (`whatsapp_outbox`):** 1 linha por número por rodada escolhida com `ROW_NUMBER() OVER (PARTITION BY session_id)` (um número cheio não trava os outros); TTL 7 dias (`charge_*` 10) a partir de `created_at` → `failed` 'expirou na fila'; `recoverStuck` falha com `attempts ≥ 3`; `payload.sent_index` retoma envio multi-mensagem sem repetir.

### 7.3 Pagamentos (§2.1 e Fase 4)
- **Nunca cobra o cartão duas vezes:** antes de cobrar o token, `attemptSavedCard` procura no Asaas por `externalReference` (id da cobrança, `billingType=CREDIT_CARD`) e **adota** um pagamento já existente (timeout/queda da tentativa anterior); rede/5xx = `unknown` → nova tentativa em 1 h, não conta como recusa. Escritas condicionais (`updateMany where status='PENDING'`) em `cancel`, `attemptSavedCard`, `publicCard`, `cardFallback`; cobrança que saiu de PENDING no meio: pago → liquida mesmo assim (dinheiro saiu), em análise → remove no Asaas.
- **Recusa × erro:** `card_attempts` conta só recusas do emissor (regex estreito; `invalid_action` genérico não é recusa); D+2/D+5 sempre às **09:00 BRT**; erro de gateway repete a cada 1 h e, vencida há > 7 dias, vira PIX. Cartão salvo em análise que o Asaas recusa depois (`FAILED`) volta para a régua (`cardDeclinedLater`). Token ilegível/removido → método `invalid` + PIX. Gateway desligado/sem chave → +1 h (não desiste). "Reenviar" nunca antecipa uma tentativa agendada (só debita se já era devida); vencimento futuro → só o aviso `card_auto`.
- **Cobrança só de cartão (página segura) expira** em vencimento + `pix_days` (e é removida no Asaas). Parcelamento é cancelado inteiro (`DELETE /installments/:id`); parcelas 2..N não aparecem como "desconhecidas" na conciliação.
- **Webhooks:** Asaas por organização (`/payments/webhook/asaas?o=<orgId>`; uma conta do Asaas serve várias orgs), token conferido por org, cobrança procurada só no provedor certo (`handleWebhookCharge` filtra `pix_provider/boleto_provider`; cartão só pela rota do Asaas); webhook removido da conta ao remover o Asaas ou apagar a org. 404 do Asaas = desconhecido (não EXPIRED) — chave trocada não "expira" cobranças antigas. Remover o Asaas é recusado enquanto há cobrança em aberto ou cartão salvo nele. Gateway principal só `mercadopago|pushinpay` (400 para outro).
- **Rotina diária:** trava por org (`dailyRunning`) e por assinatura+vencimento (`creating`) — hook da 1ª cobrança e rotina não criam em dobro; cursor por lotes de 500 (nunca para nas 500 primeiras); 1ª cobrança de cliente inativo limpa a marca. `POST /whatsapp/charges` com `payment_method_id` (debitar cartão salvo na hora) só OWNER/ADMIN. Conciliação: `truncated` (> 2000 lá), `double_paid` (dois meios pagos), `from` padrão em BRT. Página pública: erro de cartão genérico (detalhe no log).
- **Pendente (decisão):** a chave do Asaas e o `access_token` do gateway principal ficam em claro no banco (`providers.tokens`) enquanto os tokens de cartão são cifrados — cifrar exige mudar `gateways.util` (puro) para assíncrono; registrado para uma próxima rodada.

### 7.4 Front
- `CustomerDialog` só reseta ao abrir (ou ao trocar de cliente), sem perder a aba/formulário a cada salvar; "Salvar" escondido nas abas Assinaturas/Números; form de edição sem "Situação" (ações pelo ⋮); mudar o dia limpa `next_due_at`; toast da 1ª cobrança diz "será gerada" e as cobranças do painel recarregam 2,5 s depois.
- `ChargeDialog`: meio e cartão salvo vêm da assinatura; trocar de cliente limpa a seleção; toasts por resultado real do cartão. `WhatsAppCharges`: "Reenviar por PIX / boleto / link do cartão" (`{kind}`), dica de recusa na linha, `aria-label` nos ícones. `CrmGatewaysCard`: remover Asaas com confirmação e só `{remove_asaas:true}`; recarrega após testar. `PublicPay`: voo único, backoff 8→20→45 s por 15 min, só 404 é "link inválido", pendente sem meio avisa, `FAILED` rotulado, aviso de cartão salvo. `api.js`/`AuthContext`: `/pay/` nunca redireciona ao login. `todayIso` em BRT. `BILLING_STATUS.paused`. Cartões salvos: `onChanged` recarrega o cliente e `canManage` só dono/admin.

### 8.3 Motor — `WhatsAppEntitlementsService` (`back/src/whatsapp/whatsapp-entitlements.service.ts`)
- `syncSubscription(orgId, subId)`: lê assinatura + produto + regras + cliente; para cada regra faz upsert da linha com `desired` (e `kind/ref/label/session_id` atuais da regra); regra removida do produto → `desired='revoked'`. - Gatilhos: hook **`subscription_event`** (novo, ver 8.6) → `syncSubscription` (fila por assinatura em memória, debounce 2 s); `@Cron` diário 09:10 BRT (12:10 UTC) `syncAll` (cursor por lotes de 500 das assinaturas `overdue|paused|active` com produto que tem regras) — é o que aplica `suspend_after_days`; produto salvo com regras mudadas → `syncProduct(orgId, productId)` (enfileira as assinaturas vivas do produto).
- Worker (tick 20 s, claim atômico `updateMany where id, status, desired, next_try_at<=now → next_try_at = now+5min`): aplica a diferença `status → desired`:
  - `group_member`: ativar = `openwa.addGroupParticipants(sid, gid, [target])`; resultado do participante com `success:false` e status 403/408 (privacidade: só por convite) e `invite_fallback` → envia pelo **outbox** (kind `entitlement_invite`, dedupe `ent:<id>:invite`) a mensagem "Seu acesso ao grupo *{{label}}* está liberado: <inviteLink>" e marca `active` com `error='Entrou por convite (privacidade do contato)'`; suspender/revogar = `removeGroupParticipants`; número não é admin / grupo não existe → erro claro ("O número X precisa ser administrador do grupo Y").
  - `tag`: ativar = `attendance.changeTags(org, key, [tagId], [])` em toda conversa individual do cliente (todos os números); suspender/revogar = remove a etiqueta.
  - `digital_file`: ativar = outbox (kind `entitlement_file`, dedupe `ent:<id>:file`) mandando o documento (`media_id`) + texto "Aqui está o seu acesso: {{label}}"; suspender/revogar = só muda o status (não há como "desenviar").
  - `external`: nenhuma ação (só status + webhook).
  - Sucesso → `status = desired`, `attempts=0`, `error=null`, `last_sync_at`, `activated_at|suspended_at|revoked_at`; emite hook **`entitlement_changed`** `{orgId, entitlement (linha), from, to}`.   - Org sem acesso ativo (`access.isOrgActive`) → pula. Número desconectado → +30 min sem contar tentativa.
- Endpoints (JWT, `/whatsapp/entitlements`, controller novo `whatsapp-entitlements.controller.ts`): `GET ?customer_id&subscription_id&status&page` (shape: id, customer_id, customer_name, subscription_id, product_name, rule_id, kind, label, ref, session {id,label,color}, target_phone, desired, status, attempts, error, next_try_at, activated_at, suspended_at, revoked_at, updated_at); `POST /:id/retry` (dono/admin; status failed → pending, attempts 0, next_try_at now); `POST /sync {subscription_id}` (dono/admin, força `syncSubscription`); `GET /whatsapp/groups/:jid/admin-check?session_id=` → `{ is_admin, name, participants_count }` (para o editor de regras avisar).

- `admin.removeOrganization` apaga `whatsapp_entitlements`, `org_api_keys`, `org_webhook_deliveries`, `org_webhooks`. Apagar cliente: CASCADE. Apagar assinatura: SET NULL → `removeSubscription` antes revoga as linhas (`desired='revoked'`, e o worker remove do grupo) — feito pelo motor via hook `subscription_event` kind `deleted`.

### 9.6 Decisões de execução (13/10/2026) — o que ficou diferente/além do texto acima
- **Reserva**: READ COMMITTED + lock na linha do recurso (não SERIALIZABLE — com o lock no recurso a serialização é explícita e não gera os deadlocks de gap lock do SERIALIZABLE). Mesma regra no `reschedule`. Deadlock/lock wait → até 3 tentativas (`withRetry`).
- **Vagas**: o SERVIÇO (duração) precisa caber na janela e fora dos bloqueios; o intervalo de limpeza depois dele pode passar do fechamento ou entrar num bloqueio (ex.: corte 14:00–15:00 + 15 min de limpeza com bloqueio às 15:00 = vaga válida). Entre agendamentos o intervalo conta (`ends_at` inclui o buffer).
- **Política `refund`**: os gateways não têm estorno automático hoje → vira **crédito** do cliente (`whatsapp_customer_credits`) com `custom.refund_requested = true` e aviso no log, para a equipe estornar à mão se quiser.
- **Falta automática** (`by:'system'`) **não manda mensagem ao cliente** (só a falta marcada pela equipe avisa, se `notify`); conta em `custom.no_shows` do cliente e notifica a equipe.
- **Eventos/hooks emitidos**: `appointment_booked | paid | confirmed | canceled | rescheduled | reschedule_requested | expired | no_show | done | updated` (`hooks.emit('appointment_<ação>')` + `wa:appointment`). Notificações do painel: `appointment_booked`, `appointment_canceled`, `appointment_no_show` (grupo "Agenda" no catálogo, ligados por padrão).
- **Bot**: `waitlist_join.product_id` aceita `'current'` (padrão: o serviço escolhido no "Agendar" anterior — ex.: ligado à porta "sem horário") e `'ask'`; condição de cliente ganhou `no_shows` (faltas, `lt|gt`); condição de agenda (`evalAppointmentRule`) = `has_upcoming`, `has_pending` (aguardando pagamento) e `next_in_hours` (`lte` padrão, `lt|gt|gte`); textos extras além dos listados (`details`, `choose_action`, `confirmed`, confirmação de cancelamento com a política) e variáveis `{{agendamento.situacao|pagamento|prazo_cancelamento}}` + `{{agendamentos.lista}}`.
- **Painel**: `POST appointments` aceita `ignore_notice` (encaixe da equipe: ignora antecedência mínima e limite de dias; continua recusando horário que já passou há > 15 min) e `notify:false`.
- **Testes**: util puro `docs/tools/wa_schedule_util_test.mjs` 46/46; E2E `docs/tools/wa_scheduling_e2e.mjs` 35/35 (org temporária; Asaas sandbox para o PIX da reserva; **10** reservas simultâneas numa aula de 3 vagas → exatamente 3 — 50 do plano bateria no limite de 60/min da rota); bot E2E com os cenários de agenda 95/95; capturas `docs/tools/wa_fase6_shots.mjs`.

Chaves internas reservadas não podem ser campo: `first_charge, trial_charge, paused_from, status_before_pause, readjusted, notified, plan_credit, usage_cycle, due_cents, waitlist_id, refund_requested, fields`. `whatsapp_charges` ganha a coluna `custom JSON`.

- Aplicada em: clientes, produtos, assinaturas, cobranças, chamados, agendamentos e pedidos (criação e edição por painel/API; criação pelo bot).
- **Variáveis**: `{{cliente.custom.x}}` (e o antigo `{{cliente.x}}`), `{{assinatura.custom.x}}` e `{{produto.custom.x}}` (assinatura mais próxima do vencimento), `{{chamado.custom.x}}`, `{{pedido.custom.x}}`, `{{cliente.unidade}}`, `{{cliente.codigo_externo}}`.

### 11.7 Decisões de execução (13/10/2026) — onde o código ficou diferente do texto acima
- **Pagamento do pedido**: só `pix`, `on_delivery` e `none`. O `link` saiu (não há geração de link de pagamento avulso para pedido; fica reservado no util). `payment_status` é separado do andamento: pedido "na entrega" fica `not_required` e anda normalmente; PIX nasce `pending`, vira `paid` pelo hook da cobrança e, se ainda estava `new`, vai para `confirmed`.
- **PIX que vence ou é cancelado** (hooks `charge_expired`/`charge_canceled`): pedido ainda `new` e não pago é **cancelado** sozinho (`cancel_reason` "PIX não pago") e o cliente é avisado — exceto quando o pedido veio do bot (o próprio bloco segue pela porta `expired`/`canceled`).
- **Cobranças internas**: cobrança criada por pedido ou agendamento vai com `__internal: true` → não exige os campos personalizados obrigatórios de COBRANÇA (o obrigatório vale para quem cria a cobrança à mão no painel/API). Importação de clientes também pula obrigatórios (`skipRequired`).
- **PIX do pedido**: `send` = `source !== 'bot' && notify !== false` (o bot manda o PIX dentro do próprio bloco pela fila, via `charges.resend`; o painel pode criar sem avisar).
- **Sub-permissões**: `users.modules` guarda o marcador `whatsapp:basic` quando o admin tira TODAS as sub-permissões de um MEMBER (sem ele, "nenhuma marcada" não se distinguia de "usuário antigo sem marcação" = todas). DTOs do admin aceitam `MODULES + SUB_PERMISSIONS + 'whatsapp:basic'`.
- **Modelos**: arquivos `.ts` em `back/src/whatsapp/templates/data/` (não JSON em `docs/`), com marcadores `@product:` `@tag:` `@stage:` `@resource:` `@category:` resolvidos na aplicação.
- **Bot (pedidos e campos)**: o bot pergunta um campo personalizado quando ele tem `ask_in_bot` **ou** `required` (obrigatório sem perguntar faria o cadastro pelo bot falhar); no máx. 15 campos por bloco; opções de lista numeradas; freio de **5 pedidos por hora por conversa**; o simulador recebe `crm_fixture.custom_fields`/`orders`/`catalog`/`order_settings` e o front passa o `custom_field_map` ao simulador.
- **`GET/PUT /whatsapp/crm-settings`** devolve `custom_fields` (mapa) **e** `customer_fields` (lista, compatibilidade com telas/integrações antigas); `PUT` aceita lista (= clientes) ou mapa.
- **Limite do simulador**: 180 chamadas/min por IP (testes longos esperam e repetem no 429).
- **Pagamento na retirada**: `paymentMethodLabel(pm, delivery)` (`wa-order.util.ts`) — `on_delivery` com `delivery.mode='pickup'` = "Na retirada" (status "Paga na retirada"); vale no bot, nas mensagens e no painel.
- **Modelos — ordem do `apply`**: campos → **etiquetas** → produtos (com `resolve` dos marcadores, para `entitlement.rules[].ref = '@tag:…'`; regra cujo alvo não foi criado sai do produto e vai em `skipped.entitlements`) → funil → chamados → agenda → pedidos → fluxo. Reaplicar cria só um fluxo novo (nome com a data); o resto é pulado por nome. Palavras de reinício dos fluxos de modelo: `menu/inicio/início/#inicio` (sem "0", que é cancelar/voltar nos blocos de pedido e chamado). E2E `docs/tools/wa_templates_e2e.mjs` (servidor; `LOCAL_DIST=` para rodar local) e `docs/tools/wa_templates_front_check.mjs` (validação do construtor).

Rotas de escrita também exigem a sub-permissão `whatsapp:settings` (MEMBER). O ritmo da org vai até 120/min, o do número até 60/min.
- **Rotina diária**: `crm.varsForCustomers(org, rows)` (variáveis `{{cliente.*}}` em lote, mesmo resultado do `varsForChat` mas pelo cliente da cobrança, sem procurar conversas em todos os números); `subscriptions.recordEvents` (eventos em lote, mesmos hooks, `event_id` nulo); dedupe dos lembretes pela chave da fila `charge:<id>:<which>:<dia>`; direitos de acesso com `SYNC_CONCURRENCY = 4`. Sem envio de nada fora da fila.
- **Importação**: cobranças do saldo e do histórico são gravadas direto em `whatsapp_charges` (o `charges.create` sempre chama o gateway): saldo = PENDING `origin:'import'` sem PIX e sem `sent_at` (o atendente usa "Reenviar" para gerar o PIX — a régua só lembra cobranças já enviadas); histórico = PAID `paid_via:'import'` sem `settle` (assinatura não avança, sem recibo, sem webhooks). Reimportar não duplica (mesmo cliente + valor + dia). Arquivo apagado ao terminar. Máx. 3 jobs abertos por org; `.xlsx` recusado com instrução.
- **Auditoria**: além do escopo, entram `/org/api-keys` e `/org/webhooks` (sem a chave crua) e pausa/retomar/ritmo da fila; uma linha só por "apagar dados" (o interceptor pula a rota, o serviço grava). O item de menu "Auditoria" aparece para todos (o menu só filtra por um papel); a página explica quando o usuário não tem acesso.
- **LGPD**: só contatos exclusivos do cliente são anonimizados (número compartilhado com outro cliente fica); todos os vínculos `whatsapp_customer_contacts` saem (o bot deixa de reconhecer o número); no Asaas não há rota para apagar o token do cartão — fica apagado só aqui. Exportação limitada a 5.000 mensagens por conversa e 20.000 no total (`truncated`).

## 13. Revisão geral das 9 etapas (14/10/2026) — o que mudou depois das fases

Lista completa e item a item em `docs/revisao-geral-assinaturas-2026-10-14.md`. O que muda o contrato:

- **Caminho normalizado no controle de acesso** — `normalizeApiPath()` (`platform-billing/modules.const.ts`: decodifica, minúsculas, junta barras, tira a barra final) em `AccessInterceptor` e `OrgAuditInterceptor`. O Express casa rotas sem diferenciar maiúsculas e aceita barra no fim; antes `/WhatsApp/finance` e `/whatsapp/customers/` passavam sem módulo/sub-permissão. Regra nova de rota só vale se for escrita em minúsculas.
- **Sub-permissões finais** — `whatsapp:finance`: cobranças, financeiro, `whatsapp/payment-methods`, `customers/:id/payment-methods`, `orders/:id/mark-paid`. `whatsapp:crm`: lista/exportação de clientes, assinaturas (leitura + eventos), direitos de acesso, importações, cupons. `GET /whatsapp/metrics` não exige finance: para MEMBER sem finance o controller devolve `charges: null`. Escolher cliente sem crm: `GET /whatsapp/customer-pick?q=` (id, nome, código, telefone).
- **Cobrança com finalidade** — `whatsapp_charges.purpose` (`order` | `appointment` | null; migration `20261018100000_whatsapp_review_fixes`). Quem cria passa `__purpose` e `__expires_minutes` no DTO interno. Cobrança com `purpose` fica fora de lembretes, etiqueta de inadimplente, `charge_overdue`, multa/juros, marcação de assinatura atrasada e recibo do `settle`; o PIX vence em `__expires_minutes` (pedidos: `orders.pix_minutes`, padrão 60).
- **Cartão salvo** — só cobrança `recurring`/`bot` herda o cartão da assinatura; manual/API precisa de `payment_method_id` explícito (dono/admin).
- **Fila de envios** — worker com tique de 1 s, um worker por número (até 8 em paralelo), lotes de 20, ritmo por número (máx. 60/min). Antes de enviar, `staleReasons` cancela a linha se a cobrança não está mais PENDENTE com o mesmo PIX ou se o agendamento foi cancelado. `resend`/`reissue` cancelam os lembretes já na fila. Poda: `sent`/`canceled` > 15 dias, `failed` > 30 dias. `redactForJids(org, jids)` zera o payload das linhas de um cliente.
- **Rotina diária** — cursor `id > último` (sem `cursor+skip` do Prisma), lotes de 500.
- **Importação** — coluna `billing` (avulso/mensal/trimestral/semestral/anual); `next_due` no passado rola para o 1º vencimento ≥ hoje; sem `next_due` = 1º vencimento ≥ hoje; documento diferente num número já usado = cliente novo; saldo reimportado não duplica; chaves `custom` desconhecidas descartadas; histórico importado fora de Vendas.
- **Webhooks de saída** — escolha justa por webhook (`ROW_NUMBER() PARTITION BY webhook_id`; no máx. 2 em voo por webhook, 8 no total), disjuntor por webhook, desliga após **100 falhas seguidas** ou **≥ 10 falhas sem nenhuma entrega certa em 24 h** (antes: 20 falhas), entrega pendente expira em 7 dias, ponte com concorrência 4. Evento novo **`customer.erased`**.
- **LGPD** — apagar pode ser repetido (o `erased_at` é gravado por último); redige a auditoria do cliente; suprime webhooks do cliente durante o apagamento (`erasing.registry.ts`); apaga entregas antigas com os dados dele; zera `vars` das sessões do bot; zera o payload da fila; cliente apagado recusa edição/vínculo/importação (400). Telefone compartilhado não sai do grupo do WhatsApp se outro cliente ativo usa o mesmo número.
- **Auditoria** — também em `GET /org/audit` (fora do módulo WhatsApp, só dono/admin); `document_id` mascarado.
- **Agenda/chamados** — runners filtram no SQL e não travam em org desligada; lembretes D-1/H-2 não releem os enviados; resposta "1/2" ignora conversa com o bot esperando resposta; remarcação com trava; lista de espera com claim; `book()` respeita a grade `slot_minutes`; datas inválidas = 400.
- **Pedidos/financeiro/modelos** — PIX pago depois de cancelar o pedido avisa a equipe; marcar pedido pago liquida a cobrança (entra na receita); financeiro respeita os números do usuário; CSV neutraliza fórmulas; reaplicar modelo não sobrescreve configuração já salva e trava aplicação simultânea.
