### Gotchas descobertos NESTE deploy (já corrigidos no runbook/templates)
1. **Yarn 1 no lugar do 4:** sem `packageManager` no `package.json`, o corepack resolve `yarn` = 1.22 → install do back falha (engine check do `@prisma/streams-local`, Node ≥ 22). Fixado `yarn@4.10.3` no back e nos 2 micros (o front já tinha).
2. **Node 20 é EOL** (abr/2026) e o Prisma 7 pede ≥ 22 → servidor em Node 22 LTS.
3. **`CI` definido (mesmo `CI=0`) = Yarn imutável** → "Failed with errors" sem lockfile. `unset CI` antes do install.
4. **`.cnf` do MySQL com 600 é ignorado** (usuário `mysql` não lê) — buffer pool ficou 128 MB até `chmod 644`. Cuidado com `umask 077` vazando de blocos de segredos.
5. **`WEBCHAT_DOMAIN_BIND_PROVIDER`** só aceita `CERTBOT|NONE|DISABLED|MOCK` — o `.env.example` dizia `nginx` (inválido → exceção ao verificar domínio). Corrigido p/ `CERTBOT`.
6. **`NEST_WEBHOOK_URL`** precisa terminar em `/webhooks/email` (micro concatena `/schedule-sent/:id`). Corrigido no `.env.example`/README.
7. **`STRIPE_SECRET_KEY` vazio derruba o boot** (`BillingService` lança no construtor) → placeholder `sk_test_disabled_placeholder` + `VITE_STRIPE_ENABLED=false`.
8. **sshd drop-in:** o `Include` fica no topo e vale o **primeiro** valor → drop-in de hardening precisa se chamar `00-*.conf` (o `99-` perdia pro `50-cloud-init.conf` da Hostinger).
9. **`tail`/`grep` num pipe mascaram falha** (`yarn install | tail && echo OK` imprimia OK com erro). Sempre `set -o pipefail` + testar artefato (`test -d node_modules/@nestjs/core`, `test -f dist/src/main.js`, `grep -c "error TS"`).

### Gotchas de config (IMPORTANTES — valem em qualquer servidor; exemplos com `bluewebchat.online` são da AWS antiga)
1. **Runtime do banco usa `DATABASE_HOST/USER/PASS/NAME/PORT`**, NÃO `DATABASE_URL` (`back/src/prisma/prisma.service.ts`). `DATABASE_URL` só serve ao CLI do Prisma (migrate/generate). Os dois coexistem no `back/.env`.
2. **`DATABASE_POOL_LIMIT=10`** é obrigatório no `back/.env`. O adapter MariaDB mantém `minimumIdle = connectionLimit` e o back abre ~5 pools; com o default (50) ele quer 250 conexões e estoura o `max_connections=151` ("Too many connections"). Com 10 → 50 conexões estáveis.
3. **`WEBCHAT_BACKEND_INTERNAL_URL=http://127.0.0.1:8000`** (default do código é `:3000`; sem isso o `/ads.txt` dos domínios de cliente quebra).
4. Micros em loopback no `back/.env`: `IA_SERVICE_URL=http://127.0.0.1:4000`, `EMAIL_SERVICE_URL=http://127.0.0.1:9999`. email-micro precisa de `NEST_WEBHOOK_URL` (callback interno) e `BASE_URL_API=https://api.bluewebchat.online` (pixel/tracking público).
5. **ffmpeg/ffprobe** é dependência (upload de vídeo em posts). **`sharp`** é dependência do back (otimização de imagem do e-mail em `email-marketing/assets`) — instalado no server (vips 8.15.3) e no `back/package.json`; é opcional em runtime (fallback sem otimizar). **nginx serve `/uploads` direto do disco** (bloco `location ^~ /uploads/ { alias /opt/pub-mail/back/uploads/; expires 365d; add_header Cache-Control "public, immutable"; }` no vhost `pubmail-api`, antes do `location /`) — imagens do e-mail não passam pelo Node.
6. `system_settings` (singleton id=1) guarda `webchat_edge_ip` (= `3.15.235.224`) e `certbot_email` — já semeados. Sem isso, provisionamento de domínio de cliente falha.
7. Front no build precisa de `VITE_APP_BASE_NAME=/` e `VITE_API_URL=https://api.bluewebchat.online`.
8. **Timezone + horários quebrados:** servidor e MySQL rodam em **UTC**. O usuário escolhe a hora do agendamento de e-mail em **Brasília**. O `EmailSchedule.decide` (`back/src/cron-jobs/domain/email_schedules_domain.ts`) compara **minuto-do-dia** (0..1439) em **`America/Sao_Paulo`** via `Intl.DateTimeFormat` (não usa `getHours/getMinutes`, que dariam UTC). **`time` no banco = minuto-do-dia (0..1439)** — suporta horários "quebrados" (ex.: 11:30 = 690). Migration `..._schedule_time_minute_of_day` converteu os valores legados de hora (0..23) para minuto-do-dia (×60), em `email_projects_schedules.time` e `email_projects_schedules_sent.schedule_time`. O **cron tica a cada minuto** (`@Cron('0 * * * * *')`), com `run_at` em precisão de minuto (idempotência via `@@unique(project_id, schedule_id, run_at)`). Front usa `<TextField type="time">` e envia `time` = hora×60+minuto; exibe HH:MM via helper `minToHHMM`. `date` (one-off) = meia-noite UTC do dia escolhido. **Disparar agora** (`executeManualDispatch(projectId, templateId?)`) aceita template específico ou aleatório. **Reenvio para não-abridores** (`resendToUnopeners(org, projectId, sentId, subject?)` no runner; endpoint `POST /email/projects/:id/schedules-sent/:sentId/resend-unopened` + `GET .../unopened-count`): reusa o `body_html` do disparo original e reenvia só para inscritos ativos que NÃO estão em `email_schedules_sent_opens` daquele disparo (util `getUnopeners`), com assunto opcional novo. Front: ícone "Reenviar p/ não-abridores" (`ForwardToInboxRoundedIcon`) em cada card de Envios (`Sents.jsx`) → dialog com contagem ao vivo + assunto editável.

### Assinaturas do Pub Mail + módulos por usuário (FEITA, 26/09/2026)
Superadmin vende **acesso à plataforma**: cria o cliente com **módulos** liberados + **preço** + **período** (N dias ou vitalício). Conta pendente/vencida recebe uma **tela de pagamento PIX que trava tudo**; conta grátis recebe **modal de boas-vindas**. Plano completo/decisões em `docs/plano-assinaturas-acesso.md`.
- **Decisões:** plano/pagamento é por **organização** (`organization_access`); módulos são por **usuário** (`users.modules` JSON — na mesma conta um pode ter Configurações e outro não). "Administração" não é módulo (só role SUPER_ADMIN). Período **sempre conta do dia do pagamento** (`access_until = paid_at + dias`, renovação não soma ao anterior). **Vencido = tudo para** (crons/bots/webchat e quiz públicos). Aviso ≤ 3 dias antes, no máx. 2×/dia. Preço/período novos valem na próxima cobrança; preço 0 = FREE na hora; preço > 0 sem nunca ter pago = PENDING na hora. ### Módulo Telegram — Hardening anti-flood + botão copiar PIX + fix grupos (ago/2026)
Rodada de correção após bug real de produção: **"broadcasts não enviaram" + bot "digitando infinitamente"**.
- **Causa raiz (flood-ban do Telegram):** o bot levou `429 Too Many Requests: retry_after ~16000s` (~4,5h!). Origem: a **mensagem rotativa de DM** rodava o sweep **a cada 3s** (tick), ignorava o `interval`, e — pior — quando o `editMessageText` dava 429 ela **reenviava** (`sendMessage`) → **amplificava** o flood. Junto, o **worker de broadcast** também martelava: o util `telegram-api.util.call()` **não expunha `parameters.retry_after`**, então o `sendOne` usava fallback de **3s** e re-tentava a cada 3s (cada tentativa ainda mandava `sendChatAction('typing')` → o "digitando infinito"). Tudo isso mantinha o `retry_after` sempre alto (renovava o castigo).
- **Fixes (back):**
  1. **`telegram-api.util.ts`:** `TgResult` ganhou `parameters?: { retry_after? }` e o `call()` agora devolve `json.parameters` no erro. **Sem isso o retry_after real era invisível.**
  2. **`telegram-broadcasts.runner.ts`:** 429 agora honra o **retry_after REAL** (`min(retry_after, 6h)`, fallback 30s) em vez de 3s. Adicionado `cooling(botId)` + **filtro no loop**: sends de bot em flood-wait ficam PENDING e são **pulados** (polling barato de 2,5s) em vez de **bloquear o worker** (antes 1 bot floodado travava todos por horas) e sem re-hammer. `sendOne` checa `cooling` **antes** do `typing`/envio (mata o "digitando").
  3. **`telegram-rotators.runner.ts`:** `botCooldown` por bot + `note429()` que respeita o retry_after e **NÃO reenvia** em 429 (era o amplificador). Cadência mínima segura: **DM 30s** (`DM_MIN_INTERVAL`), **grupo/canal 10s** (`GROUP_MIN_INTERVAL`) — floor no runner, independente do que o usuário setar (o input aceita 5s, mas o runner protege). `dmSweep` gated por `eff` (não roda mais a cada 3s). `sleep(150)` entre contatos (~6-7 msg/s).
- **Teto de edições por lead na rotativa de DM (FEITA, ago/2026):** pra nunca mais floodar por edição excessiva de um mesmo lead. Tudo em `telegram_contacts.attributes` (sem migration): (1) **teto rígido `EDITS_PER_HOUR=10`** por lead numa **janela deslizante de 1h** (`rotator_window`/`rotator_edits`); (2) **espaçamento mínimo `MIN_EDIT_GAP` (~6 min = 3600/10)** entre edições do mesmo lead (`rotator_last_edit`) → distribui as ≤10/h ao longo da hora em vez de 10 seguidas; (3) **detecção de lead morto** (`isDeadError`: 403/"chat not found"/"bot was blocked"/"user is deactivated"/etc.) → marca `attrs.rotator_dead=true` e **PARA de editar** aquele lead (não fica editando pra sempre msg de quem saiu do Telegram). Só volta via **`bumpForContact`** (interação do lead = está vivo → limpa `rotator_dead`). Bump seta `rotator_last_edit` (não edita logo depois) e **não conta** no teto (é evento do usuário, não loop). Grupo/canal (`rotate`): guarda `isDeadError` → não fica reenviando se o bot foi expulso.
  - **Recuperação:** flood-ban só passa com **tempo** (decai sozinho quando paramos de martelar — observado 16128→14655s). Nada envia (broadcast/rotativa/pagamento) até limpar. Quando o cooldown em memória expira, os runners voltam sozinhos. **Diagnóstico:** `curl -s https://api.telegram.org/bot$TOK/sendMessage` server-side (token via DB, NUNCA no chat) → o `retry_after` no 429 é o tempo restante. Emergência: `UPDATE telegram_rotators SET active=0` pra estancar na hora.
- **Botão "Copiar código" no PIX (FEITA):** no `startCharge`, o código PIX agora vai em bloco **`<pre>`** (o Telegram renderiza um "copiar" nativo na própria bolha) + um botão **`copy_text`** (Bot API 8.0) rotulável que copia ao toque. Campo `copy_button_text` no `DEFAULT_CHECKOUT`/`mergeCheckout` (vazio = sem botão) e no front (GatewayTab → "Botão de copiar o código PIX"). Vive no JSON `checkout_config` (sem migration).
- **Bug visual — grupos "vazando pra lateral" (FEITA):** o grid de `TelegramGroups.jsx` usava `repeat(N, 1fr)`; trilhas `1fr` têm `min-width:auto` = min-content do card, e a **prévia `noWrap`** longa estourava a trilha pra fora do container. Fix: **`minmax(0, 1fr)`** (trava a trilha e deixa o `noWrap` truncar). Padrão pra qualquer grid com filho `noWrap`.
- **Aviso de flood no card do bot (FEITA):** coluna `telegram_bots.flood_until DATETIME(3)` (migration `20260826150000_add_bot_flood_until`) = até quando o Telegram barra envios. Helper `telegram-flood.util.ts` (`noteFlood`/`clearFlood`, best-effort): os runners de **broadcast** e **rotativa** gravam `flood_until` no 429 (via `noteFlood`) e limpam ao voltar a enviar (`clearFlood`/`onOk`, throttle via cooldown em memória). `toResponse` do bots devolve `flood_until` (ISO) + `flooded` (bool). Front (`TelegramSettings.jsx`): pill **"Em pausa"** (warning) + `Alert` "⏳ Pausa TEMPORÁRIA do Telegram — volta sozinho em ~Xh (por volta de HH:MM)"; texto do BANNED clarificado como **permanente** (token revogado, não volta sozinho — recadastrar). Botão de teste desabilitado durante flood. `floodEta()` calcula o relativo/horário no front; `flooded` se auto-limpa quando `flood_until` passa (sem depender de write). **Distinção:** `status=BANNED` (getMe 401 = permanente) vs `flood_until>now` (429 = temporário/auto-recupera). **Diagnóstico/manual:** setar `flood_until` na mão = `UPDATE telegram_bots SET flood_until=DATE_ADD(UTC_TIMESTAMP(3),INTERVAL <retry> SECOND)`.
- **Gotcha de DEPLOY (IMPORTANTE):** passar a **URL pré-assinada do S3 inline** no `--parameters` do SSM **falha silenciosamente** — os `&`/`%` da URL quebram o parser shorthand do `aws ssm`, o `curl` não baixa, o `tar` não extrai, mas o `nest build` recompila o código VELHO e o `test -f dist/main.js` passa → parece que deployou (mostrou BUILD_OK) mas **não deployou**. Sintoma: `grep marcador src` = 0, mtime do `src` antigo. **Solução:** passar a URL via **base64** (`echo <b64> | base64 -d > /tmp/url.txt` na instância, depois `curl $(cat /tmp/url.txt)`), e **sempre validar** com `grep -c <marcador> <arquivo>` no `src` E no `dist` antes/depois do build.
